# BRØNS Human Performance Operating System

## Product direction, not a delivery commitment

Martin's personal Human Performance Operating System is a permanent reference, learning platform, practice tool and data/analysis system. Training is one use case. The present dashboard and Strength 2.0 are an incremental foundation, not the permanent information architecture. This vision guides boundaries; it does not authorize implementing every capability now.

## Domains and shared capabilities

Five equal domains organize expertise: **Physical Performance**, **Sleep & Recovery**, **Nutrition**, **Mental Performance**, and **Health & Physiology**. Strength, running and mobility belong within Physical Performance. Domains can contribute to the same practice, experience, goal or insight; they must not become separate copies of history and storage.

| Shared capability | Long-term responsibility |
|---|---|
| Today / Command Center | Daily priorities, plans, quick tools, practices and logging across domains; a projection of authoritative records |
| Knowledge Base | Searchable principles, skills, tools, protocols, exercises, evidence and sources; useful without personal logs |
| Train / Practice | Planned and completed practice across all domains, linked to versioned definitions |
| Performance Experience Library | Real-world situations, use of tools, AAR/reflection and reusable lessons |
| Data & Insights | Source-aware history, trends, comparisons and later cross-domain analysis |
| Goals / Missions | Historical, current and future intentions, milestones and outcomes spanning domains |

These capabilities are views and workflows over shared records, not six isolated databases. A goal need not be a race; a practice need not be physical exercise. An experience can occur outside scheduled practice.

## Connected learning lifecycle

**Knowledge → tool/protocol → practice → real-world use → AAR → measured outcome → learning/adaptation**

Use stable, typed record references and explicit relationships. Content references pin revisions so later protocol edits cannot rewrite what was practiced. A real-world experience can link several practices, tools and goals; an AAR can refer to that experience; outcomes can reference independent measurements and their conditions; learning can propose an adaptation and identify its supporting evidence.

The chain is optional and many-to-many, not a mandatory linear form: outcomes may precede reflection, missing measurements stay unknown, and learning can arise without a measured outcome. Record association does not establish causation. Keep measured, estimated and self-reported evidence distinct. Adaptations remain proposals until explicitly accepted; retain prior versions and the rationale for changes.

Shared references identify entity kind, ID, relevant domains and revision when applicable. Personal records additionally retain ownership, dates/timezone, provenance and revision history through repository boundaries. Reusable knowledge and private experiences/reflections have different access policies. Private records must not enter this public static repository. Future importers must preserve source IDs, coverage and deduplication; Intervals coach plans remain read-only and distinct from completed activity.

## One product on mobile and desktop

Mobile prioritizes daily operation: Today, quick tools, low-friction logging and guided practice. Desktop uses responsive space for knowledge browsing, charts, long histories, side-by-side comparison and planning. Both use the same records, definitions and permissions; neither becomes a separate product or data silo. Responsive layouts and progressive detail must preserve access to the same capabilities, with touch/keyboard accessibility. Current navigation is transitional; this phase does not replace it or add empty destination screens.

## Current phase and future gates

Now: document these boundaries, reserve shared domain/reference contracts, and keep working features intact. No new runtime collections, storage migration, scores, automatic adaptations or cross-domain analytics are introduced by this vision update.

Later, validate one workflow at a time before implementing its schemas, validation, persistence and responsive UI. Reuse existing activity, measurement and goal records through adapters rather than duplicating them. Implement durable authenticated storage and recovery before promising permanent personal history. Agree source quality and comparison rules before analytical claims.

Mental Performance remains a first-class domain with provisional boundaries for skills/protocols, daily practices, AAR/reflection, stress regulation, identity/values, pressure performance and progression/history. The existing Mental content is a legacy view. Final content, workflows, metrics and migration await the validated Mental Performance specification from the main chat.
